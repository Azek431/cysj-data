创游世界脚本与编辑器行为解析（整理优化版）

说明：
- 本文基于用户观察、实验与逆向式推测整理。
- 其中一部分内容属于经验结论，另一部分属于尚未完全验证的推断，阅读时应区分“已观察现象”和“原因解释”。
- 为了便于后续纳入知识库，本文尽量改写为结构化表述，并保留原有核心信息。

一、关于脚本编译与运行机制的推测

1. 创游编辑器底层很可能使用 JavaScript 作为脚本执行载体。
2. 模块化内容转成 JS 代码的时机，推测更接近“点击保存”时完成，而不是在“试玩”或“发布”时才临时编译。
3. 编辑器存在较多异常处理与边界处理不完善的问题：
   - 某些错误可能被 try/catch 吞掉；
   - 某些传入对象或参数没有被充分校验；
   - 因此会出现“有 bug 但不一定报错”的情况。
4. 一个值得注意的观察是：地图物体与当前地图对象之间，可能并没有做足够彻底的对象隔离。根据现有观察，二者存在共用部分对象结构的可能性，这可能会导致一些难以理解的联动或异常行为。

二、地图结构的观察结果

一个地图的结构，大致可理解为：

当前地图
├─ 背景
├─ 自定义层级
│  ├─ 图层 1
│  │  ├─ 未命名
│  │  │  └─ （用于管理地块）
│  │  ├─ 物体
│  │  ├─ 物体
│  │  └─ ……
│  └─ 其他层级
└─ 镜头

补充说明：
- 其中“未命名”这一层，观察上更像是用于管理地块的数据容器。
- 其他节点则更接近普通地图物体或层级节点。

三、关于数组与数据组织的经验结论

1. 借助当前对象结构，可以间接做出多种形式的数组数据组织。
2. 这种方法适合用于组织配置表、列表型数据或某些自定义结构。
3. 但并不是所有内容都能直接加入，例如：
   - 某些配置型积木；
   - 含有指令语义的积木；
   - 含有特殊属性结构的积木。
4. 因此，这种“模拟数组”的方法虽然灵活，但依然存在类型和结构限制。

四、关于 3.x 中查看脚本代码的现象

1. 在 3.x 版本中，可以通过“查看数值”这一方式，查看某个“脚本”属性内部对应的代码内容。
2. 这说明脚本积木在内部应当会被转换为某种代码表示，而不是单纯以可视化积木形式永久保存。
3. 这也是进一步分析创游脚本实现方式的重要入口。

五、关于“文本转脚本”的尝试与结论

1. 曾尝试通过某种方式，把“文本类型”内容转换成“脚本类型”，但目前没有成功。
2. 根据观察，脚本内部很可能存在一个生成器，会根据积木块的位置、连接关系、属性等信息，生成一段结构化文本。
3. 这段文本中可能包含：
   - 真实逻辑代码；
   - 某些内部标识；
   - 一些看起来像哈希或随机标识符的内容。
4. 目前还不能确定它的精确生成规则，但可以确定：脚本并不是简单“把文本直接当代码执行”。

六、关于类型转换的现象

1. 创游内部存在一些自动或半自动类型转换行为，但并不总是稳定。
2. 例如：
   - 在一个数字数组里放入真假值；
   - 读取显示时，`true` 可能表现为 `1`，`false` 可能表现为 `0`。
3. 这说明底层在某些场景中会进行布尔值到数字的隐式转换。
4. 但这种转换并不是在所有情况下都成功，因此会出现“有时能转，有时失败”的情况。
5. 编辑器内也存在显式的类型转换思路，例如“文本拼接”积木：
   - 其参数通常可以接受多种类型；
   - 输出则统一转成文本类型。

七、为什么不能直接通过修改文本来改写脚本

1. 如果只看变量层（例如 `local.v1` 这类局部变量），文本变量在内部通常会被双引号包裹。
2. 理论上，似乎可以通过构造特殊文本，尝试把文本内容“嵌入”到代码结构中。
3. 但实际上，创游会对文本中的 `"` 和 `\` 等内容进行转义处理。
4. 这意味着：
   - 文本会被安全编码；
   - 很难通过简单修改文本内容来直接篡改脚本结构。
5. 因此，“通过文本修改脚本代码”的方案目前基本不可行。

八、关于“把脚本转成文本”的可行方向

1. 可以通过“文本拼接”等方式，把某些内容转为文本。
2. 也可以借助“查看数值”等能力，把脚本相关内容复制到剪贴板，进行分析。
3. 需要注意的是：
   - 这种查看脚本代码的方法主要能在 3.x 中使用；
   - 3.x 并不支持 4.x 的全部积木，因此覆盖范围有限。
4. 即便如此，这依然是目前观察脚本底层实现的有效路径之一。

九、示例代码

以下是一段通过观察获得的脚本代码示例：

```js
(evtParam) => {
  return this.getRuntime()?.awaiter(this, function* () {
    try {
      let bp = false,
        fId = "11358168_CustomComp_BrFfizH158owN_kokZfyV7N",
        eId = this.gameObject.eId++,
        local = { evtParam };

      if (bp) {
        bp = yield this.getRuntime().debug.awaitClickExecute(this.gameObject, eId, 6);
      }
      this.getRuntime().debug.addLog(this.gameObject, "BrH4hbcfwW2Qh", "数字", 123);

      if (bp) {
        bp = yield this.getRuntime().debug.awaitClickExecute(this.gameObject, eId, 7);
      }
      this.getRuntime().debug.addLog(this.gameObject, "BrH4hbfUC26sh", "真假值", true);

      if (bp) {
        bp = yield this.getRuntime().debug.awaitClickExecute(this.gameObject, eId, 8);
      }
      this.getRuntime().debug.addLog(this.gameObject, "BrH4hbjzH8a4h", "文字", "ABC");

      if (bp) {
        yield this.getRuntime().debug.awaitClickEnd(this.gameObject, eId);
      }
    } catch (e) {
      cc.log(e);
    }
  });
}
```

十、从示例代码能看出的信息

从这段代码里，至少可以观察到以下几点：

1. 脚本执行结构接近生成器/协程风格：
   - 使用了 `function*` 与 `yield`；
   - 说明异步流程可能被包装成某种运行时调度逻辑。

2. 运行依赖一个统一的 runtime：
   - 例如 `this.getRuntime()`；
   - 说明脚本执行、调试、等待点击等能力，很可能都挂在统一运行时对象下。

3. 调试系统是显式接入的：
   - 例如 `debug.awaitClickExecute`；
   - 例如 `debug.addLog`；
   - 说明编辑器调试功能并不是额外外挂，而是脚本执行链中的一部分。

4. 内部存在若干自动生成的标识符：
   - 如 `fId`；
   - 如 `BrH4hbcfwW2Qh` 这类字符串；
   - 这些内容很像节点 ID、函数 ID、积木 ID 或调试锚点。

5. 局部变量采用对象形式组织：
   - 例如 `local = { evtParam }`；
   - 这说明事件参数与局部变量有可能统一归入某个局部上下文对象。

十一、这种研究方法的优缺点

优点：
1. 相比纯猜测，直接观察“伪源代码”更有效。
2. 可以更具体地理解积木对应的底层执行方式。
3. 能帮助分析：
   - 参数传递形式；
   - 运行时对象结构；
   - 调试系统接入点；
   - 类型转换和局部变量组织方式。

缺点：
1. 技术门槛仍然存在。
2. 能获取到的代码量有限。
3. 3.x 无法覆盖 4.x 的所有新积木。
4. 获取到的代码中含有不少自动生成标识，增加了阅读难度。
5. 目前仍无法直接完成“文本 → 脚本类型”的逆向构造。

十二、当前阶段可成立的总结

1. 创游脚本系统很可能最终会落到 JavaScript 风格的运行结构上。
2. 脚本积木在内部应当会被转换成某种代码表示，而不是仅保存为纯可视化积木。
3. 3.x 的“查看数值”能力，是研究底层脚本结构的重要入口。
4. 创游内部存在类型转换，但规则并不完全透明，也不总是稳定。
5. 通过文本直接伪造脚本结构，目前看基本不可行。
6. 如果要继续深入研究，最有效的方向仍然是：
   - 系统观察更多积木转换后的代码；
   - 记录不同积木对应的 runtime 调用模式；
   - 对比 3.x 与 4.x 在底层表示上的差异。

十三、建议的后续研究方向

1. 尽量收集更多 3.x 中可查看的积木代码样本。
2. 对不同类型积木分类整理，例如：
   - 变量类；
   - 条件分支类；
   - 循环类；
   - UI 类；
   - 调试类；
   - 组件控制类；
   - 事件广播类。
3. 建立“积木 → runtime 调用”的对照表。
4. 专门记录：
   - 哪些地方会发生隐式类型转换；
   - 哪些转换是稳定的；
   - 哪些转换容易失败。
5. 继续验证地图对象、地图物体、层级节点之间是否存在对象复用或共享结构。

如果后续还有更多原始观察记录，建议继续用这种“现象 / 推测 / 证据 / 结论”的格式整理，这样更适合进入知识库长期维护。
