## 1. 这篇文档解决什么问题

很多人在创游世界里不是不会做单个功能，而是：
- 会做按钮
- 会做血条
- 会做背包
- 会做敌人

但一旦功能开始变多，项目就会很快失控：
- 变量乱放
- UI 直接改真值
- 所有逻辑塞一个对象
- 改一个地方牵一串
- 后期完全不敢动结构

这篇文档的目标不是给你一个唯一正确答案，而是给你一个 **最小可维护项目模板**。

## 2. 一个项目最少要分哪几层

建议至少分成 4 层：

### 2.1 对象执行层
负责：
- 玩家
- 敌人
- 子弹
- 掉落物
- 可交互物体
- 地图机关

这一层主要处理“对象自己该做什么”。

适合放：
- 移动
- 播放动作
- 碰撞检测
- 局部状态
- 自身血量
- 自身冷却

不适合放：
- 全局胜负
- 全图货币总量
- UI 总刷新调度

### 2.2 地图共享层
负责同一地图中的公共真值与公共流程。

适合放：
- 当前波次
- 关卡进度
- 地图内公共资源
- 已激活机关状态
- 地图级广播协调

### 2.3 系统流程层
负责更高层的流程控制。

适合放：
- 切图
- 胜负判定
- 全局计时器
- 全局音频流程
- 跨地图流程状态

### 2.4 UI 显示层
负责：
- 显示血量
- 显示货币
- 显示背包
- 接收按钮点击
- 展示弹窗

关键原则：
> UI 更偏显示与输入，不应该变成真值大脑。

## 3. 一个推荐的最小项目拆法

## 3.1 玩家对象
建议负责：
- 输入响应
- 自身移动
- 自身动作切换
- 自身生命状态
- 自身攻击触发
- 向外发事件

不建议负责：
- 全局商店库存
- 地图总任务状态
- 所有 UI 的直接刷新

## 3.2 敌人对象
建议负责：
- 自己的 AI 行为
- 自己的血量
- 命中/死亡反馈
- 死亡时发事件

## 3.3 地图控制对象
建议单独准备一个类似“地图控制器”的对象，用于统一处理：
- 地图公共广播
- 波次推进
- 地图事件开关
- 地图级数据源

## 3.4 UI 控制对象 / UI 页面
建议负责：
- 读数据并显示
- 按钮点击后发广播
- 只做轻逻辑

关键原则：
> UI 不要直接成为所有系统的真值中心。

## 3.5 系统级流程
适合统一管理：
- 游戏结束
- 返回大厅
- 切换地图
- 总倒计时

## 4. 真值与显示必须分开

这是项目能不能长期维护的分水岭。

### 错误写法
- UI 文本上的数字就是货币真值
- 血条长度本身就是血量真值
- 背包格子当前显示内容就是背包真实数据

### 正确写法
- 货币真值存在地图属性/系统属性/玩家状态里
- UI 只是读取后显示
- 背包数据有自己的数据源结构
- 格子只是把数据渲染出来

一句话：
> **显示层只是脸，真值层才是脑。**

---

## 5. 广播在项目里怎么用

广播最适合做“通知”，不适合做“藏得过深的复杂黑箱流程”。

### 推荐场景
- UI 点击“购买” → 广播给地图/系统处理购买
- 玩家击杀敌人 → 广播通知任务系统、掉落系统、UI 系统
- 关卡条件满足 → 广播通知 UI 弹窗和流程推进

### 不推荐场景
- 所有细碎局部计算都走广播
- 广播名完全随手写，没有命名规范
- 一个动作要穿过十几层广播才知道发生了什么

推荐命名思路：
- `ui.open_bag`
- `shop.buy_item`
- `battle.enemy_dead`
- `task.progress_add`
- `map.wave_start`

## 6. 数据放哪：一个简单判断法

### 放局部变量
如果它只是临时计算中间值。

### 放自身属性
如果它属于某个对象自己的状态。

例如：
- 当前血量
- 是否在冷却
- 当前目标

### 放地图属性
如果它是当前地图里多个对象共享的数据。

例如：
- 本局总击杀数
- 地图内货币池
- 当前波次

### 放系统属性
如果它涉及更高层全局流程或跨地图状态。

例如：
- 全局设置
- 全局结算流程
- 全局统计

## 7. 一个小项目也应该遵守的结构纪律

### 7.1 不要把所有脚本写在一个对象上
这会导致：
- 找不到入口
- 依赖链混乱
- 后期难拆

### 7.2 不要让 UI 到处直接改底层状态
这会导致：
- 逻辑分散
- 很难排错
- 联机同步更难稳

### 7.3 不要一开始就做“大而全”
建议先做最小闭环：
- 输入
- 状态变化
- 反馈显示
- 完成一次完整流程

### 7.4 不要让变量命名随意
尤其是：
- 地图属性
- 系统属性
- 广播名
- 结构体字段

这些必须尽量稳定。

## 8. 一个可维护项目的最小闭环示例

以“购买药水”为例：

1. UI 点击购买按钮
2. UI 发广播 `shop.buy_item`
3. 地图/系统逻辑收到广播
4. 判断货币是否足够
5. 若足够，扣真值货币
6. 更新背包数据源
7. 发广播通知 UI 刷新
8. UI 重新读取并显示

这里的关键不是步骤多，而是：
- 真值有统一来源
- UI 不直接私自乱改
- 各层职责比较清楚

## 9. 最适合先模板化的几个系统

建议优先把这些系统做成“结构模板”：

1. 货币系统
2. 背包系统
3. 血量与血条系统
4. 商店系统
5. 任务推进系统
6. 地图波次系统

因为这些系统最容易在多个项目里反复出现。

---

## 10. 常见失败信号

如果你的项目出现以下情况，通常说明结构开始坏了：

- 一个对象里脚本多到自己都找不到
- 同一个值在 UI、地图、对象上各存一份
- 每加一个功能就要改 5 个地方
- 改血量逻辑时背包也出 bug
- 广播名字完全无规律
- 你只能靠“记忆”维持项目，而不是靠结构

---

## 11. 一句话模板总结

一个更稳的创游世界项目，通常应该遵守这句：

> **对象负责执行，地图负责共享，系统负责流程，UI负责显示与输入，广播负责解耦，真值与显示必须分离。**
