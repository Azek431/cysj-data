# 社区分析待验证问题清单

## 1. 文档目的

本清单用于集中记录目前知识库中还不能完全写死、仍需要截图补证、OCR 补页或实机验证的问题。

这样做的好处是：
- 避免把推测误写成事实
- 后续补图时知道先补哪类最值
- 让社区分析和官方证据保持边界

---

## 2. 当前待验证的主要方向

### 2.1 编辑器 / 脚本底层执行模型
当前已有不少来自 `资料/其他用户给的解析.txt` 的观察，但很多仍属于：
- 伪源码猜想
- 保存后结构推测
- 3.x / 4.x 可观察性差异下的间接判断

需要继续做：
- 补更多旧版本材料
- 补更直接的界面/行为证据
- 明确哪些部分只是研究视角，不是官方定义

### 2.2 OCR 中的低清页或无效页
目前 OCR 文档中仍有：
- 无有效文本页
- 文字残缺页
- 需要人工复核的页

需要继续做：
- 原图恢复或重新取得后，再对低清页重新 OCR
- 在映射表里补状态标签
- 对关键页做人工修正

### 2.3 云变量 / 持久化边界
目前已有更新线索与架构归纳，但仍缺更系统的官方说明证据整合。

需要继续做：
- 搜更多更新页
- 从教程或界面截图中补字段证据
- 在项目型文章里标注“归纳”与“直接说明”的边界

### 2.4 联机 UI 演进中的旧逻辑边界
当前已经有 4.52.x ~ 4.54.0 的主线，但某些旧版限制与推荐实践仍有继续补证空间。

### 2.5 云变量、任务系统、交互系统的直接证据密度仍不足
当前这几类专题已经能形成较稳定的结构化建议，但其中一部分仍偏“多来源归纳”，直接来自官方截图的细粒度证据密度还不够高。

需要继续做：
- 从引擎更新页补云变量上限、命名变更、兼容边界
- 从教程页补可互动对象、任务相关界面或组件线索
- 在专题文档中继续区分“直接证据”和“工程归纳”

---

## 3. 当前处理原则

### 3.1 能确认的写成结论
如果有：
- 官方教程原文
- 引擎更新原文
- 界面截图直接证据

则可作为明确结论整理。

### 3.2 不能确认的保留为线索
如果只有：
- 社区观察
- OCR 残缺信息
- 单页模糊线索

则保留为“待验证”而不是直接写死。

---

## 4. 建议优先验证的事项

### P0：优先级最高，补完后能显著提升全库可信度
1. 脚本界面剩余高价值 OCR 号段
2. 官方教程中 UI / 数据类型 / 武器 / 地图结构的未补页
3. 引擎更新老版本中与调试、云变量、联机限制相关的截图页

### P1：高价值结构性问题
4. 社区分析中与伪源码、地图节点结构相关的关键猜想
5. 云变量、任务系统、交互系统的直接证据密度不足问题
6. 联机 UI 演进中旧版限制与新实践之间的边界差异

### P2：中长期补强方向
7. 低清页、重复页、无效页的统一状态清洗
8. 研究型文档中“直接证据 / 工程归纳 / 推测线索”的边界重标

---

## 5. 建议修复闭环

为了避免“只记录问题、不推动解决”，后续建议每个待验证事项都按下面闭环处理：

1. **提出问题**：明确当前到底缺什么证据
2. **定位来源**：对应到截图编号、OCR 文档或专题文章
3. **补证据**：补 OCR、补原图、补更新页、补交叉引用
4. **降级或升级结论**：
   - 证据充分：升级为明确结论
   - 证据不足：保留为待验证
   - 证据冲突：显式写出边界与版本差异
5. **回写索引**：同步更新映射表、总索引和专题文档

这个闭环的核心目的，是把“研究线索”逐步转化为“可回溯结论”。

---

## 6. 当前文档自我复盘

从知识库当前状态看，待验证问题主要存在以下不足：

- 有些问题描述了方向，但缺少更细的编号级定位
- 有些专题已经比较成熟，但“证据等级”表达还不够醒目
- 某些结论虽然合理，却还没有形成“截图编号 → OCR → 专题结论”的完整链路
- 少数地方存在“研究计划”与“事实索引”混放的倾向，容易影响检索清晰度

因此，后续优化重点应放在：

- 把问题进一步编号化、对象化、主题化
- 把待验证项和已确认结论分层展示
- 把修复动作写成可执行清单，而不是只保留口头方向
