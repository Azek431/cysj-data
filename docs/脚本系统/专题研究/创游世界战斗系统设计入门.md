# 创游世界战斗系统设计入门

## 1. 文档目标

这篇不是逐条罗列所有战斗积木，而是回答一个更实战的问题：

> **如果我要在创游世界里做一个能打、能掉血、能显示反馈、还能继续扩展的战斗系统，最小架构应该怎么搭？**

适合对象：
- 已经会基础摆物体、挂组件、写一点脚本
- 想从“会拼功能”进到“会搭系统”
- 打算做 RPG、横版动作、射击、闯关、Boss 战

---

## 2. 战斗系统最小骨架

可以先用一句话记：

> **战斗系统 = 战斗对象 + 战斗组件 + 状态数据 + 命中流程 + UI反馈 + 可扩展规则**

最小闭环通常至少包含：
- 攻击者
- 受击者
- 生命值
- 伤害来源
- 命中或触发条件
- 受伤后的状态变化
- UI 或表现反馈

如果缺少其中任一环，系统就容易“能播动作但不扣血”或“扣了血但玩家看不出来”。

---

## 3. 从现有证据能确认什么

### 3.1 战斗类组件存在清晰分类
根据脚本界面截图，可直接确认战斗分类至少包含：
- 生命
- 伤害
- 武器槽
- 远程武器
- 近战武器
- 子弹

这意味着创游世界并不是把战斗全部塞进一个黑箱组件里，而是把战斗拆成多个职责模块。

### 3.2 这套拆分很像标准游戏架构
可以粗略理解为：
- `生命`：负责承受伤害、记录血量
- `伤害`：负责定义或处理伤害行为
- `武器槽`：负责装备/切换/持有武器
- `近战武器`：负责近身攻击类逻辑
- `远程武器`：负责投射/射击类逻辑
- `子弹`：负责飞行物或命中载体

这比“一个对象自己处理所有战斗逻辑”更容易扩展。

---

## 4. 推荐的战斗对象分层

### 4.1 角色本体层
角色本体更适合承载：
- 生命值
- 阵营
- 当前状态（受击、闪避、死亡、霸体等）
- 移动/朝向
- 武器槽

### 4.2 武器层
武器更适合承载：
- 攻击方式
- 攻击参数
- 冷却时间
- 命中范围
- 子弹生成规则

### 4.3 子弹 / 命中特效层
子弹或攻击体更适合承载：
- 飞行表现
- 命中检测
- 命中后广播/触发
- 命中特效
- 自动销毁

### 4.4 UI 层
UI 更适合承载：
- 血条显示
- 伤害数字
- 技能冷却
- 武器/弹药显示
- 受伤提示

别把核心扣血逻辑写死在 UI 里。UI 负责显示，地图/对象脚本负责真实状态。

---

## 5. 一个标准受伤流程该怎么想

推荐把“攻击命中”拆成这几步：

1. 攻击动作开始
2. 生成攻击判定或子弹
3. 命中目标
4. 判断是否允许受伤
   - 是否同阵营
   - 是否无敌
   - 是否已死亡
   - 是否在特殊状态
5. 计算伤害
6. 扣除生命
7. 触发反馈
   - 飘字
   - 受击动画
   - 击退
   - 音效
   - 血条变化
8. 判断是否死亡
9. 若死亡，进入掉落/结算/广播

这样设计的好处是：以后你要加暴击、护盾、Buff、破甲、元素伤害，都有位置可插。

## 6. 状态应该放在哪里

### 6.1 放在自身层的状态
适合放角色自身属性：
- 当前生命值
- 最大生命值
- 当前是否无敌
- 当前是否闪避中
- 当前装备武器
- 当前攻击冷却

### 6.2 放在地图层的状态
适合放地图公共状态：
- 当前波次
- 敌人总数
- 剩余敌人数
- 本局总击杀数
- 战斗是否开始
- Boss 是否已登场

### 6.3 放在系统层的状态
适合放全局流程：
- 游戏胜负
- 总计时器
- 联机公共变量
- 跨地图战斗状态

## 7. 血条系统为什么总是核心练手题

B站上“血条系统”类视频很多，不是巧合，而是因为它刚好把几个核心子系统串起来：
- 生命值
- 伤害
- UI
- 动画或渐变
- 数据同步

也就是说，谁把血条做好了，通常已经开始摸到真正的系统设计。

一个完整血条至少要想清：
- 它读谁的生命值
- 它什么时候刷新
- 它是直接绑属性，还是通过广播更新
- 它是否要做平滑变化
- 它是否区分“即时血条”和“延迟血条”

## 8. 动作战斗为什么会引出状态机问题

像跑步、闪避、翻滚、滑铲这类功能，看起来只是动作，实际上会逼你面对状态机：
- 正在跑步时能不能攻击？
- 闪避期间能不能受伤？
- 翻滚期间要不要隐藏血条或伤害提示？
- 受击时能不能打断当前动作？

如果这些规则不清楚，战斗系统会变得很乱。

所以推荐至少有一个最简状态表：
- 待机
- 移动
- 攻击
- 受击
- 闪避
- 死亡

然后逐步定义：
- 哪些状态能进入哪些状态
- 哪些状态会锁输入
- 哪些状态免伤
- 哪些状态结束后回到待机

## 9. 推荐的第一版项目实现顺序

如果你现在就要做，建议按这个顺序：

### 第一步：做角色生命系统
先有：
- 最大生命
- 当前生命
- 扣血
- 死亡

### 第二步：做最小攻击闭环
先不求华丽，只做：
- 攻击动作
- 命中目标
- 扣血

### 第三步：做血条显示
把角色状态可视化。

### 第四步：做一种武器
选近战或远程先做一种，不要一起上。

### 第五步：补表现
- 飘字
- 受击反馈
- 震动/变色/闪烁
- 音效

### 第六步：补状态系统
- 闪避
- Buff
- 冷却
- 无敌帧

### 第七步：再做系统化扩展
- 多武器切换
- 子弹类型分化
- 概率触发另一种子弹
- 背包携带战斗道具
- UI 与地图广播解耦

## 10. 很常见的几个坑

### 坑 1：把所有逻辑都写在一个对象里
结果会变成后期一改就炸。应拆给：角色、武器、子弹、UI、地图。

### 坑 2：UI 直接控制真实战斗结果
UI 更适合发请求，不适合做最终裁决。

### 坑 3：攻击判定和伤害结算混成一块
以后加护盾、暴击、减伤会很难插进去。

### 坑 4：状态不分层
把临时变量、角色状态、地图流程、全局流程混着放，后面联机会特别痛苦。

### 坑 5：一开始就追求大而全
推荐先把“能打 + 能掉血 + 能显示”做稳定，再往上加花活。

## 13. 结论等级与待验证问题

### 已确认
- `[已确认]` 从现有脚本界面截图可以直接确认，战斗相关能力并不是一个黑箱，而是至少拆成生命、伤害、武器槽、近战武器、远程武器、子弹等多个类别。
- `[已确认]` UI 不应作为真实扣血与战斗结果的最终裁决层，它更适合作为反馈显示层。

### 高可信推断
- `[高可信推断]` 把战斗对象拆成角色本体、武器、子弹/攻击体、UI 四层，会比把逻辑堆在一个对象里更适合后续扩展。
- `[高可信推断]` 先搭“生命—命中—扣血—反馈”的最小闭环，再补武器、Buff、状态机，是大多数项目更稳的实现顺序。

### 待验证
- `[待验证]` 不同版本的具体组件参数、默认行为与可组合方式，可能与当前截图主证据存在差异。
- `[待验证]` 联机环境下战斗状态同步、伤害结算归属与 UI 延迟显示，仍需专题级进一步验证。

## 14. 常见误区补充
- 许多人把“攻击动作播放出来了”误认为“战斗系统已经成立”，但如果没有命中、状态判断和反馈闭环，本质上还只是表现层。
- 一开始就做多武器、多段连招、复杂 Buff，通常会掩盖底层命中流程和状态边界还没稳定的问题。
- 只盯着单个战斗教程，很容易学会一个效果，却学不会可扩展的职责拆分。

## 12. 当前结论

基于现有资料，可以先得出一个很实用的结论：

> **创游世界的战斗系统并不是一块“战斗黑箱”，而是由生命、伤害、武器槽、近战、远程、子弹、UI 反馈和状态控制共同拼出来的。**

所以真正有成长价值的，不是“背会某个战斗教程”，而是学会：
- 怎么拆职责
- 怎么放状态
- 怎么让 UI 和对象逻辑分开
- 怎么给以后扩展留接口
