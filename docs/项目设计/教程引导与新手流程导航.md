## 教程引导最重要的设计观念

- `[已确认]` 引导本质上是一组“条件 → 提示 → 完成 → 下一步”的流程控制。
- `[已确认]` 引导信息和引导状态应尽量分开。
- `[已确认]` UI 高亮、文字提示、任务目标和交互检测不应混成一个脚本大杂烩。
- `[高可信推断]` 如果项目后面内容很多，教程系统最好尽早做成可配置、可跳过、可恢复的结构。

## 推荐拆分方式

### 引导状态层
负责：
- 当前进行到第几步
- 该步是否完成
- 是否允许跳过 / 回退 / 重新触发

### 条件检测层
负责：
- 玩家是否完成指定点击
- 是否进入指定地图
- 是否获得指定物品
- 是否打开指定 UI

### 提示展示层
负责：
- 文本提示
- 箭头 / 高亮 / 遮罩
- 对话框 / 引导弹窗

### 推进控制层
负责：
- 完成当前步骤
- 切换到下一步骤
- 处理中断、退出、重进

## 常见误区

- 误区 1：把所有教程逻辑硬写在一个页面脚本里。
  - 后果：流程稍一复杂就难改。
- 误区 2：只做“显示提示”，不记录步骤状态。
  - 后果：玩家重复触发或中断后很容易乱套。
- 误区 3：教程和主任务互相打架。
  - 后果：流程源头不清，条件冲突频繁出现。
