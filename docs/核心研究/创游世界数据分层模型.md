# 创游世界数据分层模型

## 一句话摘要

创游世界的数据不是单层的，而是分为局部变量、自身属性、地图属性、系统属性四层。理解「这个值该放哪一层」，是避免项目越做越乱的关键一步。

## 适合谁阅读

- 刚学完基础脚本，想做完整项目的开发者
- 项目越做越乱，找不到数据在哪的创作者
- 想理解为什么广播比直接调用更稳定的人

## 你将学到什么

- 四层数据模型的定义与特点
- 每层适合存放什么数据
- 四层之间的数据流向
- 常见的数据分层错误
- 推荐的架构设计原则

## 1. 为什么要单独理解数据分层

在创游世界里，很多看似「改了但没效果」的问题，本质上都是数据放错了层。

例如：
- 在 UI 里修改了一个值，以为地图会同步，结果没有
- 在一个物体里存的变量，切地图后就消失了
- 广播发出去后，不知道谁该处理、谁该保存

这些问题不是脚本不会写，而是没有想清楚「这个数据该归谁管」。

创游世界把数据分为四层，每层有不同的生命周期、作用域和适用场景。只要搞清楚这个，项目架构就会清晰很多。

## 2. 四层数据模型详解

### 2.1 局部变量：临时工

**定义**：在单次脚本执行过程中临时创建和使用的变量，执行完就消失。

**特点**：
- 生命周期最短
- 仅在当前脚本块内有效
- 通常用于暂存计算结果、拼接文本、临时判断

**适合存放**：
- 一次计算中的中间结果
- 条件判断的临时标记
- 避免重复读取同一属性的缓存值

**示例**：
```
新建局部变量 为 0
设置局部变量1 为 玩家.金币
设置局部变量1 为 局部变量1 - 10
如果 局部变量1 >= 0 则
    设置玩家金币为 局部变量1
```

这里 `局部变量1` 只在这次购买流程里有用，结束后自动消失。

**不要用它存**：
- 需要跨脚本、跨对象保留的状态
- 需要切地图后仍然存在的数据
- 多界面需要共享的值

---

### 2.2 自身属性：对象的私有数据

**定义**：挂载在某个物体或组件上的属性，记录该对象自己的状态。

**特点**：
- 与具体物体绑定
- 随物体存在而存在
- 适合记录「这个东西现在怎么样」

**适合存放**：
- 当前血量
- 是否在冷却中
- 当前状态（如「待收割」「已激活」「翻滚中」）
- 物体自身的开关、计数、阶段

**示例**：
```
如果 自身属性.当前状态 == "未收割"
则
    设置自身属性.当前状态 为 "已收割"
    播放动效 收获动画
    向当前地图发广播 "增加一个收获"
```

这里的状态属于这个物体本身，切地图后如果物体消失，状态也跟着消失。

**不要用它存**：
- 需要跨物体共享的数据
- 需要跨地图保留的数据
- 全局流程控制变量

---

### 2.3 地图属性：场景的公共数据

**定义**：属于当前地图的全局数据，当前地图内所有物体都可以读写。

**特点**：
- 作用域是整个地图
- 随地图切换而重置（取决于具体实现）
- 适合存放关卡级状态

**适合存放**：
- 当前波次
- 地图倒计时
- 机关总开关状态
- 地图内收集品计数
- 当前任务阶段（如果是地图级任务）

**示例**：
```
当收到广播 "怪物被击杀"
则
    设置当前地图属性.击杀数 为 当前地图属性.击杀数 + 1
    如果 当前地图属性.击杀数 >= 当前地图属性.目标击杀数
    则
        向当前地图发广播 "本波完成"
```

这个计数是地图级的，多个怪物死亡都会修改同一个变量，不需要每个怪物单独记。

**注意**：
- 如果联机，不同玩家修改同一个地图属性可能有同步问题
- 建议地图属性修改集中在地图脚本，而不是分散在多个物体里

---

### 2.4 系统属性：全局共享数据

**定义**：跨地图、跨流程的全局数据，作用域最广。

**特点**：
- 整个游戏全局生效
- 通常用于全局配置和跨地图状态
- 滥用会让项目耦合严重

**适合存放**：
- 全局难度设置
- 玩家总进度
- 跨地图状态（如「第一章是否完成」）
- 全局开关（如「是否已经教程引导」）

**示例**：
```
当玩家开始游戏
则
    如果 系统属性.难度 == "困难"
    则
        设置当前地图属性.敌人倍率 为 1.5
```

这里的难度是全局配置，不是某个地图私有的。

**警告**：
- 不要把所有变量都放系统属性
- 这样做会让所有逻辑都耦合在一起
- 后续极难维护

## 3. 四层对比速查表

| 层级 | 生命周期 | 作用域 | 典型用途 | 联机同步 |
|------|---------|--------|---------|---------|
| 局部变量 | 单次执行 | 当前脚本 | 临时计算、中间值 | 不需要 |
| 自身属性 | 物体存活期 | 当前物体 | 对象状态 | 需注意同步策略 |
| 地图属性 | 地图存活期 | 当前地图 | 关卡级共享数据 | 集中在地图层 |
| 系统属性 | 游戏存活期 | 全局 | 全局配置、跨地图状态 | 谨慎使用 |

## 4. 数据分层与UI的关系

### 4.1 为什么UI不直接保存真值

UI显示的值 ≠ 真值来源。

例如：
- UI 上显示金币 100
- 但真值可能存在「地图属性」或「系统属性」里
- UI 只是把真值「读出来并显示」

如果 UI 直接保存金币值：
- 切地图时可能丢失
- 联机时不同步
- 多个界面显示可能不一致

### 4.2 推荐的UI与数据分层配合

```
UI 层：显示 + 接收输入
     ↓ 发广播/请求
地图层：真值 + 公共逻辑
     ↓ 修改状态
     ↓ 发广播刷新
UI 层：接收刷新 → 更新显示
```

这就是为什么常说「UI 只管显示和输入，真值放在玩法层」。

## 5. 数据分层的常见错误

### 错误一：把所有数据都放系统属性

**后果**：
- 所有物体都直接读写全局变量
- 系统耦合严重
- 排查问题不知道谁改的

**正确做法**：
- 先问：这个数据只和这个物体有关吗？→ 放自身属性
- 再问：这个数据需要地图内共享吗？→ 放地图属性
- 最后才问：这个数据真的需要全局吗？→ 才放系统属性

### 错误二：用局部变量存持久状态

**后果**：
- 下一次脚本执行时变量已经消失
- 表现为「刚才还有值，现在没了」

**正确做法**：
- 需要持久的数据，放自身属性、地图属性或系统属性
- 局部变量只用于「这次计算用一下」的场景

### 错误三：让UI直接改玩法数据

**后果**：
- UI 层承担了太多职责
- 联机时性能问题
- 逻辑分散，难以维护

**正确做法**：
- UI 发广播表达「请求」
- 地图脚本接收并处理
- 地图脚本修改真值
- 再通知 UI 刷新

### 错误四：让多个物体同时改同一个地图属性

**后果**：
- 联机时数据冲突
- 难以追踪修改来源

**正确做法**：
- 地图属性修改集中在地图脚本
- 其他物体通过广播触发地图脚本处理
- 不要让多个物体各自直接修改地图属性

## 6. 推荐的架构设计原则

### 原则一：先局部，再自身，然后地图，最后系统

```
临时值 → 局部
单对象状态 → 自身
场景共享 → 地图
全局配置 → 系统
```

每升高一层都要有明确的理由。

### 原则二：真值集中，UI分散

- 真值（影响玩法的数据）集中在玩法层
- UI 只负责显示和接收输入
- UI 修改通过广播/请求，不直接改真值

### 原则三：广播表达意图，不表达实现

```
✅ 好：发广播 "请求购买"
❌ 差：发广播 "扣钱、生成道具、更新背包、刷新货币显示"
```

广播名称应该表达「想做什么」，而不是「具体怎么做」。

### 原则四：每个数据有且只有一份真值

如果同一个数据在多处存在：
- UI 显示一份
- 地图属性一份
- 系统属性一份

就容易出现不同步。

解决方案：
- 真值只存在一个地方
- 其他层只读取或通过接口修改
- 修改后发广播通知所有需要同步的地方

## 7. 实战例子：从买道具看数据分层

### 场景

玩家在商店界面点击「购买」，扣除金币，生成道具。

### 错误做法

在 UI 脚本里：
```
点击购买按钮
→ 扣减 UI 显示的金币
→ 生成道具物体
→ 播放音效
```

问题：
- 金币值在 UI 里，联机时不同步
- 如果从背包再次打开商店，金币显示可能不一致

### 正确做法

**UI 脚本**：
```
点击购买按钮
→ 向当前地图发广播 "请求购买道具"
```

**地图脚本**：
```
当收到广播 "请求购买道具"
→ 检查玩家金币是否足够
→ 如果足够
    → 扣减玩家金币
    → 生成道具
    → 向当前地图发广播 "刷新商店界面"
```

**UI 收到刷新广播**：
```
当收到广播 "刷新商店界面"
→ 读取当前金币值并显示
→ 更新背包显示
```

这样：
- 金币真值在地图/玩家变量层
- UI 只负责显示和发送请求
- 联机同步更容易处理

## 8. 常见问题

**Q：局部变量和自身属性有什么区别？**

A：局部变量只在当前脚本执行中存在，执行完就消失；自身属性绑在物体上，只要物体存在就一直保留。

**Q：地图属性和系统属性有什么区别？**

A：地图属性只管当前地图，系统属性跨地图全局生效。能用地图属性解决的就不要用系统属性。

**Q：联机时数据应该放哪层？**

A：联机时：
- 玩家级数据放玩家变量或系统属性（取决于同步需求）
- 地图级数据集中在地图脚本处理
- 避免在 UI 里直接连续修改公共数据
- 建议用广播 + 地图集中处理的模式

**Q：变量放错层会怎样？**

A：轻则表现不符合预期（切地图后数据丢失、UI 不同步），重则联机时数据混乱、项目难以维护。
