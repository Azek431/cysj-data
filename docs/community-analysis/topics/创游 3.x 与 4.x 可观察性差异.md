# 创游 3.x 与 4.x 可观察性差异

本文基于 `其他用户给的解析.txt` 中关于 3.x 观察脚本代码的描述，以及现有引擎更新与脚本资料，整理 3.x 与 4.x 在“可观察性”层面的差异线索。

> 说明：本文主要是研究线索整理，不代表官方确认结论。

## 1. 为什么研究“可观察性”

很多时候，真正限制研究深度的，不是功能本身，而是：
- 能不能看到底层表现
- 能不能拿到中间结果
- 能不能观察脚本生成后的形式

因此，3.x 和 4.x 的差异，未必只在功能多少，更可能在：
- 看得见多少
- 调得动多少
- 验证路线是否存在

---

## 2. 3.x 的关键线索：可通过“查看数值”观察脚本属性

`其他用户给的解析.txt` 提到：
- 在 3.x 中，可以通过“查看数值”查看某个“脚本”属性中的代码

这条线索非常关键，因为它意味着：
- 3.x 某些环境里，脚本并非完全黑箱
- 用户可以间接看到积木转换后的文本结构
- 可以收集“积木 -> 伪源码片段”的映射

对于逆向研究来说，这几乎是一个天然观察窗。

---

## 3. 4.x 的问题：能力更强，但黑箱更厚

从现有资料可以看到：
- 4.x 明显增加了更多积木、更多数据类型、更多系统能力
- 但社区文本同时指出：3.x 不支持 4.x 的部分积木

这形成一个研究上的矛盾：
- 3.x 更容易观察
- 4.x 更接近当前真实能力

所以研究者会遇到：
- 3.x 看得到，但不完整
- 4.x 更完整，但更难直接看底层

---

## 4. 可观察性差异的三种层面

### 4.1 代码可见性
3.x：
- 存在通过“查看数值”侧看脚本代码的可能

4.x：
- 当前资料中没有同等级别的直接可见路径被确认

### 4.2 积木覆盖范围
3.x：
- 可用于研究旧积木或基础积木
- 但无法覆盖 4.x 新能力

4.x：
- 支持更丰富的数据类型与脚本块
- 但缺乏同样方便的观察窗

### 4.3 调试方式
4.x：
- 从更新记录可知，逐行 Debug、调用栈等能力在增强

这说明 4.x 虽然可能更黑箱，但也在提供另一种官方调试路径：
- 不是直接看生成代码
- 而是看执行过程与调用关系

---

## 5. 这意味着研究方法必须分层

### 用 3.x 做什么
适合：
- 看基础积木可能生成什么形式的伪源码
- 观察 runtime / gameObject / local / evtParam 等结构
- 建立对“积木转执行逻辑”的直觉

### 用 4.x 做什么
适合：
- 验证当前真实功能行为
- 比较新积木的外部表现
- 借助官方调试工具观察调用链和执行流程

### 最佳策略
- 用 3.x 建立底层模型猜想
- 用 4.x 验证现代版本行为
- 不把 3.x 的可见结果机械套到 4.x 全部系统上

---

## 6. 为什么“文本转脚本”在 3.x/4.x 都难

社区文本指出：
- 即使看到了伪源码文本
- 也不代表能直接从文本反构造成脚本

原因包括：
- 可能有生成器
- 可能和积木位置有关
- 可能带随机/哈希标识
- 文本有转义处理

这说明“可观察性”与“可逆性”是两回事：
- 3.x 更可观察
- 但未必可逆
- 4.x 更强大
- 但也未必更开放

---

## 7. 对知识库建设的启发

这个主题提醒我们，知识库不该只按“功能分类”整理，还应该按“研究手段”整理。

例如可以建立：
- 哪些结论来自官方教程
- 哪些来自版本更新
- 哪些来自 3.x 侧观测
- 哪些来自 4.x 行为验证
- 哪些只是社区猜想

这样后续问答时就能更清楚地区分：
- 已确认事实
- 高可信推断
- 待验证假设

---

## 8. 适合 AI/RAG 的关键词

- 4.x

- 伪源码
- 调用栈
- 逐行Debug

## 9. 后续可继续深挖的问题

1. 3.x 中哪些具体积木最适合做伪源码样本收集
2. 4.x 调试工具是否能间接替代部分源码观察能力
3. 3.x 与 4.x 的 local / evtParam / runtime 结构是否一致
4. 不同版本中广播、自定义指令、组件脚本的可观察性差异
5. 如何建立“3.x 观察结果 -> 4.x 行为验证”的研究链路
